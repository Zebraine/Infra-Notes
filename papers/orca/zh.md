## 摘要

面向生成任务的大规模 Transformer 模型（如 GPT-3）近来备受关注，亟需针对这类模型的服务系统支持。由于这类模型以自回归方式逐 token 生成，处理一个请求需要多次运行模型，每次迭代只生成一个输出 token。现有推理服务系统难以应对这种“多迭代”负载：其调度机制不灵活，无法改变正在处理的批；批内较早完成的请求不能先返回，新到达请求必须等整批结束。本文提出迭代级调度（iteration-level scheduling），以迭代而非请求为粒度调度执行，调度器只让执行引擎在批上运行模型的一次迭代；同时在 Transformer 上把批处理与迭代级调度结合，提出选择性批处理（selective batching），只对选定算子做批处理。基于这两项技术，我们实现分布式服务系统 Orca，并针对数千亿参数模型增加可扩展性设计。在 GPT-3 175B 上的评估表明，Orca 在延迟和吞吐上都显著优于 NVIDIA FasterTransformer：在相同延迟水平下吞吐提升 36.9 倍。

## 1 精读导读

Orca 是把连续批处理（continuous batching）引入 LLM 服务的那篇论文。在它之前，服务系统以请求为粒度调度：凑一个批，把每个请求跑完，再接纳新请求。对图像模型这没问题——一次前向就完成一个请求；但自回归 LLM 的请求可能需要数百上千次迭代，一个批会长期占用资源。短请求被长请求堵住，新请求必须等整批清空。

Orca 的解法是把调度粒度降到“一次模型迭代”。每次迭代后，调度器可以回收已完成的请求、接纳新请求、改变批的组成。论文的后半部分解决让迭代级批处理可行的系统问题：注意力的张量形状依赖每个请求当前的生成长度，不能简单拼成一个稠密张量；选择性批处理只批处理可以批的算子，注意力则逐请求执行。

今天几乎所有主流 LLM 服务引擎——vLLM、TensorRT-LLM、TGI、SGLang——都实现了某种形式的连续批处理与迭代级调度。Orca 是这个论文库中服务类论文的概念基线。

## 2 问题与背景

基于 Transformer 的生成模型每次迭代生成一个 token，并把该 token 作为下一次输入，因此一个请求需要很多次迭代。现有推理服务系统以请求为粒度调度：服务系统把一批请求交给引擎，引擎处理完整批后才一次性返回结果。不同请求需要的迭代数不同，于是批内较早完成的请求必须等最慢的请求结束后才能返回；在批派发之后到达的请求则要等整批处理完，额外增加排队延迟。

论文认为，这是自回归生成的“多迭代”特性与请求级调度之间的根本错配。正确的做法是让批在迭代之间可以变化，同时仍然对主导 GPU 时间的算子保持批处理效率。

## 3 方法

### 3.1 迭代级调度

Orca 的调度器让执行引擎在当前批上只运行模型的一次迭代。每次返回后，调度器检查哪些请求已经完成并立即返回结果，然后考虑新到达的请求，再启动下一次迭代——此时批的组成可能已经改变。这就是迭代级调度，与请求级调度相对。

调度器维护迭代级先到先服务（FCFS）策略，并使用可配置的最大批大小；批没满时，按到达顺序从等待池接纳请求。它还为已接纳请求预留 KV cache 显存，并在多个 worker 之间管理流水线执行，使一个请求的下一轮迭代能在上一轮结束后尽快开始。结果是：新请求最多等一次迭代就能加入，完成的请求可以立刻离开。

### 3.2 选择性批处理

迭代级调度会产生这样的批：不同请求已经处理过的 token 数不同。注意力算子的输入张量形状取决于每个请求当前的序列长度，因此不能拼成一个统一的稠密张量。Orca 因此采用选择性批处理：把这一批拆开，逐请求执行注意力；而 QKV 投影、MLP、LayerNorm 等其他 Transformer 算子仍然跨请求批处理。

这样做效率很高，因为注意力没有可跨请求复用的模型参数，批处理它并不能减少参数读取；真正权重密集、昂贵的 GEMM 仍然保持批处理。论文表明，逐请求执行注意力对端到端效率的影响很小。Orca 还使用层内与层间模型并行，以扩展到数千亿参数模型。

## 4 实验与结果

评估使用 13B、175B、341B 参数的 GPT-3 模型。在 GPT-3 175B 上，Orca 在延迟和吞吐上都显著优于 NVIDIA FasterTransformer。中位归一化延迟为 190 ms/token 时，FasterTransformer 只有 0.185 req/s，而 Orca 达到 6.81 req/s——相同延迟水平下吞吐提升 36.9 倍。论文在不同负载和模型规模下都报告了数量级的提升。

结果说明，在请求级调度下单纯增大批大小远不如“迭代级调度 + 选择性批处理”有效。系统还借助模型并行与流水线并行扩展到 341B 参数模型。

## 5 影响与局限

Orca 确立了后续 LLM 服务栈默认采用的调度模型。连续批处理、迭代级调度、选择性批处理如今已是基础设施的基线能力，而不再是研究想法。论文也说明，服务吞吐是调度和显存问题，而不只是 kernel 问题。

它的局限带有时代性。Orca 是研究系统，没有作为通用开源引擎发布；接纳策略是相对简单的 FCFS，对 KV cache 碎片、前缀共享、抢占等问题的处理不深——这些正是 PagedAttention 与 vLLM 下一步要解决的。论文也更关注吞吐—延迟权衡，而不是公平性或 SLO 感知调度，为后来 BidKV 这类工作留下了空间。
